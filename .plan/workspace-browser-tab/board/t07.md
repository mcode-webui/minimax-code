## Parent

199 — workspace browser tab model specification

## What to build

The Agent opens tabs, and a run with no selection is no longer a dead end.

The tool adapter resolves the surface from the run's selection and refuses with
`browser_target_unknown` when the run has selected nothing
(`packages/webui/src/runtime/browser/tool-adapter.ts:146-152`). The refusal is right and stays for
every action — but it currently reaches `open_tab` too, and `open_tab` is the action that would
create the selection the gate wants.

So `open_tab` becomes the one action a run with no selection may perform. It asks the service to
open a page; the service observes the new target, makes it the run's selection, and publishes the
new snapshot; the client shows the tab and activates it.

The refusals keep their meaning:

- The surface's switch is off → `browser_surface_not_authorized`.
- The surface cannot open a tab → `browser_capability_denied` (the bridge's case).
- Any other action of a run with no selection → `browser_target_unknown`, unchanged.

## Acceptance criteria

- [ ] A cold run's `open_tab` produces a page the same run can then navigate, and the tab appears
      in the client's strip as the active one.
- [ ] Every other action of a cold run still fails with `browser_target_unknown` — the refusal
      reaches no further than it did.
- [ ] `open_tab` on a surface whose switch is off is refused with `browser_surface_not_authorized`,
      and no page is created.
- [ ] `open_tab` on a surface that cannot open a tab is refused with `browser_capability_denied`.
- [ ] The action is an explicit bootstrap, not a default: the run's selection is only created by the
      action, never by an action that needs a selection.
- [ ] The run's selection after `open_tab` is the new page, and a second `open_tab` moves it to the
      second page without losing the first.

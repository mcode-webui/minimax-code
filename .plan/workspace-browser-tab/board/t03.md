## Parent

199 — workspace browser tab model specification

## What to build

`open_tab` creates a page that can be addressed.

Today the provider's `open_tab` calls `Target.createTarget` and returns the result
(`packages/webui/src/runtime/browser/isolated-chromium/provider.ts:473`). The page it creates is
never attached to, is never registered, and — because the provider drives exactly one page and
refuses every other target — **cannot be driven, streamed or input into at all**. It shows up in
the target list as a tab that does nothing when chosen.

The new `open_tab` creates the page, attaches to it, registers it in the provider's per-target map,
and returns its identity: the surface, the browser id, the target id, and the generation the
provider's own accounting gives it. The service observes the new target from that identity.

The action's own vocabulary does not change: `open_tab` is already in the restricted command set
(`packages/webui/src/shared/contracts/browser.ts:310-340`), so the Agent's capability declaration
is untouched.

## Acceptance criteria

- [ ] A page created by `open_tab` can be driven, streamed and input into.
- [ ] The identity the action returns names the page that was created — surface, browser id, target
      id and generation — and the service can observe it from that identity alone.
- [ ] The new page appears in the provider's target list with the same identity it returned.
- [ ] A page that is not the launch page and was not created by `open_tab` is still refused; the
      provider does not become a way to address an arbitrary page.
- [ ] The bridge's refusal is unchanged: `open_tab` on Edge or Chrome is still
      `browser_capability_denied`, because the extension drives the browser through its debugger and
      cannot open a page in it.

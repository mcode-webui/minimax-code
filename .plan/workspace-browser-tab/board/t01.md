## Parent

199 — workspace browser tab model specification

## What to build

The technical validation work package. Nothing else in this programme is written against an
assumption; this ticket establishes what is actually true before the rest depends on it.

Four things have to be settled, and each of them has a way of being wrong that no type checker
catches:

1. **The isolated provider can hold two pages, and each can be driven, streamed and input into
   independently.** Today it drives exactly one page and refuses every other target
   (`packages/webui/src/runtime/browser/isolated-chromium/provider.ts:405`, `:266`, `:317`).
2. **The generation can advance per page.** Three sites make the single-page behaviour true:
   `provider.ts:251` reports a constant `1` for every page that is not the launch page,
   `provider.ts:229` sends `Page.enable` only to the launch page's session, and `provider.ts:532`
   raises the generation only for the launch page's session. If a second page's generation never
   advances, a reference recorded against it never goes stale, and the fence that exists to make a
   stale reference detectable is dead on every tab but the first.
3. **The frame's target identity is reachable.** It is the envelope's `event.sessionId`
   (`packages/webui/src/runtime/browser/isolated-chromium/cdp-connection.ts:233-240`, a string);
   `event.params.sessionId` is the numeric screencast acknowledgement id and is not a target.
4. **The client's tab model has the sites the inventory names.** A stable id with a mutable content
   breaks the caches that are keyed by the id while their effects depend on it, and the two review
   tabs that share one id today.

The output is a written capability matrix for the tab model — what a web tab can do, what the
fence guarantees on every page, and what the registration and plumbing costs are — published in
`packages/webui/docs/browser-use/01-capability-matrix.md`, and a spike that proves the two-page
case against the real provider.

## Acceptance criteria

- [ ] A spike drives, streams and inputs into two pages of one isolated Chromium at the same time,
      and the observation is recorded rather than asserted.
- [ ] The spike shows a navigation on the **second** page advancing that page's generation and
      refusing a reference recorded against the previous one. A fence that only works on the launch
      page is a fence that does not work.
- [ ] The frame's page is resolved from the envelope's session id, and the observation says so.
- [ ] The tab-model inventory is checked against the tree: the files-tab singleton, the two review
      tabs that share one id, the label derived from the kind, the `kind === "review"` narrowing,
      the `activeTab?.kind` guards, and the caches keyed by tab id whose effects depend on
      `[activeTab?.id]`.
- [ ] The capability matrix gains a section for the tab model, and every cell in it is `measured`,
      `implemented` or `not yet measured` — the matrix's own vocabulary.
- [ ] The new operation's registration cost is written down: the capability manifest's `browser.ready`
      list, the operation-name constants, the operation registry, the server handler, the port member
      and its binding, and the transport's request table.
- [ ] The plumbing cost of a new source file and a new test file is written down: the frozen path
      metadata fixture, the declared Vitest suite groups, the source inventory, and the Playwright
      spec directory.
- [ ] If any of the four is false as assumed, ADR 0022 is amended **first**, and the affected
      tickets are re-scoped to match.

## Parent

#176 — WebUI Browser Use specification

## What to build

Four independent switches in Settings, each off until the user turns it on, each persisted so it
survives a restart, and each readable by the runtime that has to honour it: the isolated browser,
Edge, Chrome, and Full CDP access.

The switch is the only thing that authorizes a surface. A provider may exist, and browser tools may
be exposed in the tool schema, while every switch is off — and in that state the Agent must not be
able to act on a browser. This ticket establishes that vocabulary once, in one place, for every
later ticket to build on.

## Acceptance criteria

- [ ] Settings exposes four independent switches: isolated browser, Edge, Chrome, and Full CDP
      access.
- [ ] All four are off on a fresh install and stay off until the user turns them on. No upgrade,
      migration or first-run path turns one on.
- [ ] Each switch persists and is still honoured after a WebUI restart.
- [ ] The persisted state is readable by the runtime through the ordinary runtime port, and the
      client never holds a second copy of it.
- [ ] Provider presence is not authorization: with every switch off, a constructed provider and
      exposed browser tools do not make any browser operation available.
- [ ] Full CDP access is separately represented in the persisted state and cannot be inferred from
      any of the three browser switches.
- [ ] The persisted state has a declared schema with a default and a migration behaviour, and both
      are pinned by unit tests.
- [ ] An unknown, corrupt or unreadable persisted value resolves to off with an explicit error
      rather than a silent default-on.
- [ ] The authorization state is declared once as a shared contract and consumed by both the client
      and the server; there is no second, parallel shape of the same state.
- [ ] The Settings controls call the browser business through its published contract and own no
      browser state of their own.

## Source

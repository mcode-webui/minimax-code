## Parent

#176 — WebUI Browser Use specification

## What to build

The evidence every later ticket is written against, and the contracts they must not re-decide.

A reader who has not seen this feature should be able to implement against the answers: which CDP
domains and commands each surface actually exposes, what the extension bridge protocol is, how the
extension is admitted and authenticated, where a pairing credential is stored and what happens when
that store is unavailable, how the extension's service worker behaves when the browser kills it, and
how targets, generations and per-tab serialization work.

This is a validation and contract-pinning ticket. It produces published evidence and pinned
contracts, not a running feature. It is the first ticket because every other ticket assumes its
answers.

## Acceptance criteria

- [ ] A capability matrix exists for the isolated Chromium, Edge and Chrome surfaces, listing the CDP
      domains and commands each one actually exposes, the full-CDP diagnostic commands that differ
      per surface, and the version-dependent gaps. Every command a surface does not support is
      recorded as unsupported; no surface is described as having another surface's capabilities.
- [ ] The bridge protocol is pinned: protocol version negotiation, message and frame size limits,
      image delivery and back-pressure policy, cancellation semantics, health and status reporting,
      and the mapping from transport failures to stable error codes.
- [ ] The extension admission rules are pinned: loopback host, the exact supported extension identity
      per build, the per-browser pairing credential, the protocol version, message size limits and
      the per-browser switch state — and where in the upgrade lifecycle the dedicated admission hook
      sits, ahead of the generic handler.
- [ ] Pairing credentials are proven to be validated on the dedicated path even when the generic
      service runs in its development mode, so a development-mode bypass cannot bypass extension
      admission.
- [ ] The operating-system secure credential store path is recorded for every supported operating
      system, together with the explicit "store unavailable → pairing fails" behaviour. No plaintext
      credential persistence path is proposed.
- [ ] The extension's service-worker termination and restart is exercised during an active image
      stream and during an in-flight browser operation, not only between operations, and the recovery
      and error behaviour is recorded.
- [ ] The target identity and selection contract is pinned: how each Agent run owns its target, how a
      target change bumps its generation, how operations against one tab serialize while different
      tabs proceed independently, and how element references are invalidated at a target change.
- [ ] The existing runtime's browser-tool authorization and tool-exposure behaviour is traced, so
      provider construction, each default-off browser authorization and the separate Full CDP
      command gate are specified as three independent things.
- [ ] The findings are published as evidence on this issue (or an issue linked from it) and the
      downstream tickets cite them.
- [ ] If any finding requires a product change, ADR 0019 is updated first and the affected tickets
      are re-scoped before any code is written.

## Verification

This ticket produces evidence rather than code. Its verification is that every item above is
published and each claim names the browser version, the operating system and the method used to
obtain it. Any prototype used to obtain a result is described well enough to be repeated.

## Parent

#176 — WebUI Browser Use specification

## What to build

A credential lifecycle the person can reason about: each browser has its own credential, it is
stored where it cannot be read casually, turning the switch off destroys it immediately, and
turning the switch on creates a new one without asking the person twice.

After a restart, the person should still be authorized — and a credential from a browser that was
switched off must never work again.

## Acceptance criteria

- [ ] Each browser has its own distinct high-entropy credential. Edge and Chrome credentials are
      independent, and neither is derived from the other.
- [ ] The WebUI side stores the credential in the operating system's secure credential store; the
      extension side stores it in that extension's local extension storage.
- [ ] If the operating system's secure credential store is unavailable, pairing fails with an
      explicit error. No plaintext credential persistence path exists anywhere in the flow.
- [ ] Turning a browser switch off revokes the credential, closes the active sockets, and rejects
      every copy of the old credential. The extension cannot reconnect with it.
- [ ] Turning the same switch back on creates a fresh credential and establishes a new pairing, with
      no second user confirmation.
- [ ] Enabled state, authorization and pairing survive a WebUI restart and a browser restart, and the
      extension reconnects on its own.
- [ ] Credentials never appear in logs, in error messages, or in any diagnostic output.
- [ ] The lifecycle is proven with a synthetic peer: successful pairing, persistence across restart,
      credential rotation on re-enable, revocation on disable, an expired credential, and a
      credential from a browser that was switched off.
